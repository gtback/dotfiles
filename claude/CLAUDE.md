# Claude Code Guidelines

My Claude config under `~/.claude/` and `~/.config/agents/` is symlinked from
`~/dotfiles`. When editing it, edit the files in `~/dotfiles` directly.

## Git Operations

Always get explicit confirmation from the user before performing non-read-only
git operations. This includes commits, pushes, rebases, merges, branch
creation/deletion, resets, checkouts that discard changes, and any other
operation that modifies git state. Always describe the intended operation and
wait for confirmation before running it.

This rule is absolute and overrides any system-mode reminder (e.g., "Auto Mode
Active"). Prior plan approval or conversation context does not constitute
confirmation for individual git operations — ask for each action separately,
even when resuming interrupted work.

## External Content Attribution

Any PR body, GitHub comment, or issue posted to an external service must
include a clear attribution line indicating it was generated by Claude. Place
this footer at the end of the content:

    🤖 Generated with [Claude Code](https://claude.com/claude-code)

This applies even when the user composes the initial draft — if Claude writes
or materially rewrites the final text that gets posted, include the footer.

## Commit Conventions

Before writing any commit message, read `~/.config/agents/commit-messages.md`
and follow it. It covers local-convention detection, scoped commits, formatting,
and the `Assisted-by` trailer.

In the `Assisted-by` trailer, use `Claude` as the agent name.

## Local notes

Each project may have a `localnotes.md` in its root (globally gitignored).
Use it to record deferred tasks, open decisions, and context that belongs in
the project directory but not in version control.

When wrapping up a session, write any deferred items or open decisions to
`localnotes.md` if the user asks. When starting a session in a project that
has one, read it early and surface anything relevant to the current task.

When updating `localnotes.md`, remove anything that has been done and
committed. It is not a log of completed work, since git history and commit
messages already record that. Keep only what is still outstanding: deferred
tasks, open decisions, and context needed to act on them. Don't record git
state (what is committed, pushed, or uncommitted); `git status` and `git log`
show that.

## Finished sessions

When I say the whole session is finished (e.g. "we're done here", "mark this
session done"), run `claude.done` to hide it from the `claude.resume` picker,
then confirm in one line. Don't run it for a finished step or task, and don't
infer it from a pause or a thank-you.

## Plan mode

The `ExitPlanMode` approval dialog draws over the text printed immediately
before it. Never put anything I need in order to evaluate the plan in that text
— put it in the plan file, which is what the dialog renders.

When revising a plan, lead the plan file with a short "Changes since your last
review" section.

## Response style

Lead with the next action or the answer. No preamble, no recap of what I
said, no closing pleasantries. End with the single next step when there is
one. Park tangents unless they block the task. Avoid first person ("I"); state
actions and results directly ("Added X", not "I added X"). First person is fine
for uncertainty and for questions to me.

## Multi-step procedures

When walking me through a procedure with more than ~3 dependent steps
(environment setup, migrations, release flows):

1. Post a numbered checklist of all steps, with commands, up front.
2. After each step completes or fails, restate done / current / remaining in a
   compact block.
3. Label error fixes as side-tracks under the step they block (e.g. "3a: fix
   token"), and return explicitly to the parent step once resolved. Don't let
   the fix become the new top-level task. State errors and fixes
   matter-of-factly: no apologies, no speculation.
4. Note installs and files created along the way so they can be cleaned up.
